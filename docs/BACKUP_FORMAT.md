# 本地备份与跨平台迁移格式

格式名ALICEBK1，文件后缀.alicebackup，版本1。此规范是本项目协议设计，不代表已有实现。两端必须使用同一份编解码与校验测试向量。

## 1. 容器

按顺序写入：8字节ASCII魔数ALICEBK1；4字节大端无符号header长度；对应长度UTF-8 JSON header；AES-256-GCM ciphertext；16字节认证tag。

header 为 UTF-8 JSON 对象，字段固定为 format_version（整数1）、kdf（PBKDF2-HMAC-SHA256）、iterations（写入600000）、salt（16个随机字节的标准Base64）、cipher（AES-256-GCM）、nonce（12个随机字节的标准Base64）、payload_bytes（仅密文部分的字节数，不含16字节认证tag）。先核对总长度等于12＋header长度＋payload_bytes＋16再解密。AAD为魔数、长度字段及原始header字节拼接。读取时使用文件中的原始字节做AAD，不能重新序列化替代。

口令按原始UTF-8编码，不trim、不改变大小写、不隐式Unicode归一化；输入至少10个Unicode码点。使用安全随机源，每次导出新salt与nonce。PBKDF2派生32字节key。禁止固定nonce、将家长6位PIN直接当备份口令或把口令写进日志。

读取前限制：header不超过4096字节，整个文件不超过256MiB，iterations只接受600000至1200000且必须为正整数；未知算法和版本立即拒绝。先检查长度与结构，再做KDF，避免恶意参数引发无限资源消耗。新格式不通过忽略字段向后强行兼容。

## 2. 加密载荷

载荷为ZIP，只允许manifest.json和snapshot.sqlite两个普通文件；不得包含目录跳转、绝对路径、符号链接、重名条目、额外可执行文件。解压后合计不超过512MiB，manifest不超过1MiB。解压流式计数达到上限即拒绝，不信任ZIP头声明大小。

manifest字段：

| 字段 | 含义 |
|---|---|
| backup_id | 本次导出的随机UUID，不用作积分来源 |
| mode | backup或migration |
| format_version / schema_version | 容器与SQLite结构版本 |
| created_at_utc / family_timezone | 导出时间与家庭时区 |
| family_id / child_id | 原家庭与孩子稳定身份 |
| source_device_id / lineage_id | 源设备与数据血缘，仅用于诊断与迁移提示 |
| snapshot_revision | 生成快照时最后一次领域提交版本 |
| rules_version / catalog_version | 业务与商品版本 |
| required_asset_ids | 恢复完整显示所需的素材ID列表 |
| database_sha256 | snapshot.sqlite字节摘要 |
| summary | 余额、流水数、家庭有效完成数、拥有物品数、空间数和伙伴阶段。结构 8 增加当前伙伴经验及已解锁伙伴数 |

摘要只用于预览和交叉核对，真正恢复的是完整数据库。不能通过摘要重新生成任务、重放发奖或累加余额。

数据库包含家庭业务记录、规则与目录版本、物品、摆放和心愿。`child_profiles.active_pet_id`、伙伴解锁、成果归属、等级和穿戴一并迁移。设备 ID 与家庭血缘单独处理。设备 PIN 校验材料、恢复密钥、家长会话、导出密码、内部恢复点密钥和临时授权留在设备上。

## 3. 导出

1. 家长验证；选择普通备份或迁移，输入并确认口令。
2. 将新的领域写入短暂排队，等待在途事务结束，生成一致性SQLite快照。
3. 验证完整性、外键、余额等式、所有权/布局与引用；写manifest，压缩并加密到临时文件。
4. 回读临时容器，验证解密、摘要和完整结构；普通备份恢复写入，迁移模式保持冻结。
5. 通过系统文件保存能力复制到用户选择的位置。确认保存成功再登记外部导出成功；接口只确认交给系统时标为待核实，可重新选择文件验证。
6. 清理临时明文与临时密文。取消、磁盘不足、系统拒绝或中断均不得登记成功。

迁移模式只有外部文件成功保存或经用户回读验证后，才维持MIGRATION_PENDING；导出失败恢复之前的可写状态。冻结期间余额与布局不能继续变化。已生成同一迁移快照可再次保存，不能暗中重新取不同时间点仍使用同一backup_id。

保存结果未知时，持久化AWAITING_FILE_VERIFICATION并保持只读；重启不得自动解除。家长可以回读文件完成验证，或确认该迁移包未在其他设备继续使用后取消。只有确定失败或经家长明确取消才恢复写入。

## 4. 导入与覆盖

1. 从系统选择器打开文件；检查魔数、长度、算法与资源上限。
2. 输入口令并验证GCM认证；失败使用统一错误“口令不正确或文件已损坏”，不暴露内部私人信息。
3. 在新临时目录解压，校验摘要，按预期schema白名单核查表、列、索引，不执行来自文件的SQL脚本、扩展或未知触发器。打开时禁用不受信任schema行为。
4. 运行数据库完整性、外键、余额与流水一致性、所有权关系、家庭唯一性、规则及资产兼容性验证。
5. 旧schema在临时数据代中迁移并复核；未知未来schema拒绝。原数据库在此阶段不变。
6. 显示备份摘要与当前摘要。非空设备先成功生成内部恢复前副本；失败则不允许覆盖。明确确认整体替换，不提供账本合并按钮。
7. 新设备设置新PIN与恢复密钥，生成新的device_id；以新代ID暂存设备凭据，确认可读后原子替换active.json。
8. 打开新代并核对摘要，记录导入回执。保留原代供恢复，不对备份中余额或物品执行新增发放。

相同backup_id重复导入：若当前未发生后续业务变化，返回已恢复；若已有新变化，必须再次预览和确认整体覆盖。任何路径都不可累加余额。

## 5. 中断与回滚

- 构造临时新代时崩溃：下次仍打开旧active指针，清理不完整临时代。
- 新代与新凭据已写完但未切指针：仍使用旧代，待用凭据可清理。
- 指针完成切换后崩溃：下次验证并打开完整新代；若校验异常，进入恢复界面使用上一个完整代，不静默混合记录。
- 回滚须由当前有效家长身份授权；重新绑定有效凭据，不复活被撤销的旧PIN或恢复密钥。
- 导入失败不删除源文件、不修改当前数据；目标磁盘不足也必须满足该要求。

## 6. 内部恢复点

内部副本使用单独魔数ALICECP1和设备密钥，保留最近5份。密钥存平台安全存储，不进入外部备份。不将内部副本暴露为可跨设备导入的.alicebackup文件。

UI必须区分“内部恢复点”与“已导出的备份”。没有外部备份时，卸载、丢失设备或清除应用数据可能无法恢复，不能用内部副本承诺可恢复。

## 7. 迁移的使用约定

同一家庭首版仅在一个当前设备继续操作。源设备导出迁移包后只读；目标成功恢复后成为新的当前设备。用户自行传文件，目标不会向离线源设备远程回执或远程擦除。

本规范不能阻止人为复制同一备份到多台设备；不承诺离线多设备强一致。若两个副本都被继续修改，家长必须选择一份完整状态继续使用，不能自动相加积分或并集合并物品。

结构 5 沿用 ALICEBK1 容器。有效完成数等于共享经验，最高阶段取已记录授予与经验门槛中的较高值。旧结构的输入先按原版本核对摘要及认证数据，再在临时数据代升级并比对完整业务摘要。

彩窗亮起后，主线结局随存档进入目标设备。已通关再重玩仍可在家中看到三扇窗花。旧版数学书签在结局或进阶页时，更新后会接上同一个结局。

结构 6 增加《风过暖廊》的独立书签。每个家庭的孩子有一个当前轮次和五个待补窗格的位图。导入结构 1–5 的旧档时，新样片从开场开始，原来的彩窗里程碑及十九片叶子书签照常恢复。结构 6 的备份会带上本轮已经嵌入的每一片叶子。补完第五片与点亮家园在同一事务内保存，重玩时家中仍保留亮起的窗。容器继续使用 ALICEBK1，目标端需要能够读取结构 6 的家庭版。

结构 7 增加 `rain_map_runs` 和 `companion_memories`。前者记录当前轮次、这段已走石板、已盖爪印、首次完章和近路挑战。后者每只伙伴各记一次首次抚摸和首次呼唤。快照校验要求雨天地图符合前章条件。规范化业务摘要包含新表中实际存在的记录，空表保持旧结构摘要可比较。ALICEBK1 和外部摘要字段沿用原格式。结构 1–6 可用 0.17 读取，结构 7 需要 0.17 或之后的兼容版本。

结构 8 增加 `owned_companions` 和 `companion_completions`，沿用 ALICEBK1 容器。`active_companion_experience` 和 `owned_companion_count` 随摘要校验，`max_growth_stage` 记录当前伙伴的最高已获等级。结构 1–7 的旧备份先按原摘要校验，在新数据代建立当前伙伴的首宠记录，并将旧成果分配给它。切换数据代前同时核对新增归属规则与升级前已有业务记录的摘要。结构 8 的备份需要 0.21 或之后的兼容版本。

结构 9 增加 `companion_affinity_days` 和 `companion_candies`，继续使用 ALICEBK1。亲密度按伙伴累计每日首次互动和已喂食糖果。旧档中已拥有伙伴的首次回忆迁为起始亲密度，日期字段留空。糖果按兑换流水逐颗保存，未喂食、已喂食和已退回可核对。旧档激活前核对升级前已有的业务表，新档的完整摘要包含两张新表。结构 9 的备份需要 0.22 或更新的兼容版本。

结构 10 更新 `purchased_once` 部分唯一索引，允许 `affinity_candy`、`affinity_cookie`、`affinity_pudding` 重复兑换。每份食物关联原有 `purchases` 及 `companion_candies` 表，商品类型由 `purchases.item_id` 决定。升级结构 9 时只重建该索引，业务行与摘要保留。结构 10 的备份需要 0.24 或更新的兼容版本。
